# 2. How to Biuild a Game World

## 2.1 Game Objects (GO)

游戏的大部分内容都是由**Object**构成的，我们通过构建不同的**Object**，来实现游戏的内容、玩法和环境。这些对象可以认为处于引擎的Resource Layer，引擎通过对这些对象的管理和处理，能够实现我们想要实现的游戏世界。

### Static Object

静态对象一般指的就是我们游戏中的一些实实在在的物品。例如FPS游戏中的瞭望塔、房屋、各式各样的掩体等等。静态对象一般就是不进行运动的、不经常进行交互的对象。


### Dynamic Object

动态对象相对于静态对象就是我们游戏中经常需要交互的物品。还是举FPS游戏中的例子：士兵、角色、坦克、飞机、枪械等等。经常需哟交互的对象，并且对象之间也是存在很频繁的交互时，我们就可以使用动态的对象。

### Other Objects

还有很多类型的**GO**。例如环境对象、植被对象和不同类型的地形地貌。还有一些游戏的逻辑内容：游戏的玩法机制、空气墙设置、导航系统等等。**GO**是一个应用很广泛的、游戏制作中不可避免需要使用到的结构。

就是因为应用广泛的特点，**GO**的设计就存在一些问题。因为我们会有很多种类型的对象，不同的对象会有不同的属性和附属品。从而我们需要设计很多个类。如果对象的种类变多了，那么可能没什么问题，但是如果游戏的体量变大、对象数量繁多的话，这种设计模式是不靠谱的。

当代的游戏引擎设计中，我们会将**GO**分成一个个的小模块（**Component**），模块和模块之间会组成一个整体，细分种类下的**GO**就可以改变其中少数的几个模块就可以设计完成。并且也可以继承一个大的框架，并通过友元的设定来设计这些**GO**。


## 2.2 Ticking

### **Tick**函数

Tick函数是用来将静态的游戏世界运转起来的关键函数。我们设计好**GO**之后，就需要在游戏运行过程中，将这些**GO**之间，进行动态处理，即Component之间的交互。

直觉上来讲，我们肯定是会将整个**GO**全部Tick一遍之后，再和别的**GO**进行Tick（**Object-based Tick**）。但是当对象数量增多时，这样的效率会变得特别慢（根据局部性原理）。所以当代的引擎都是将所有同类型**Component**进行Tick。这样我们对一个类型的类就可以重复进行Tick（**Component-based Tick**），从而达到效率提升的目的。

## 2.3 Event

### **Event**机制

基于Component机制，Component之间需要进行通信，但是如果说每一个Component都进行监听的话，就不能得到一个效率特别高的游戏系统。所以我们使用了**Event**机制，类似于**MailBox**的机制，我们就可以将每一个Component需要做的事情作为一个Event，并将每一个Component想要完成的任务就放到MailBox，告诉别人我想要我进行了某一步的操作。

然后其他的Component就可以通过访问MailBox来查询是否有其他的Component来对我进行处理或者影响。

### Scene Management

虽然上面的方式非常有效，但是在进行判断的时候，我们还是需要打破**n^2**的挑战。在场景中我们使用最多的是**BVH**和**Octree**两种方法，这些都是基于空间数据的结构体系。

**BVH**简单来讲，是通过将物体包围起来之后，查询物体和物体之间有没有包含和被包含的关系。每一个物体或者说多个物体可以被一个包围圈包围，那么这个大的包围圈，中我们就可以找到那个小的物体。

**Octree**，即八叉树。其将空间中的物体分成八分，然后每一分中又可以被分成八分。同样的，我们就可以通过一分空间中的物体来判断是否存在一个小物体存在碰撞或者交互。
